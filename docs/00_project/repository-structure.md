# データ活用スケーリング計画 Repository 構成ガイド

> **文書版:** Draft v0.2
>
> **位置付け:** 本文書は、Repository 内の物理配置、各領域の責務境界、および構成変更の判断基準を定める正本です。情報種別ごとの正本、更新責任、参照方向は `document-governance.md` に従います。

## 1. 目的と適用範囲

本文書は、Phase 1 以降の成果物を「何を、どこへ置くか」で迷わず管理するため、初期 Repository 構成と配置ルールを定めます。対象は `docs/`、`decisions/`、`definitions/`、`data/`、`analytics/`、`.github/` です。

Repository の入口はルートの `README.md`、情報の正本・更新・参照ルールは `docs/00_project/document-governance.md`、物理配置と責務境界は本文書がそれぞれ担います。本文書は個々の成果物の内容、更新責任、Decision Record の様式、データ保持可否を個別に決定するものではありません。

## 3. 領域ごとの責務

| 領域 | 目的・配置対象 | 配置しないもの | 正本との関係 | 追加条件 |
| --- | --- | --- | --- | --- |
| [`docs/`](../README.md) | プロジェクト管理、方針、設計、運用など、人が読む説明文書 | Decision Record、機械処理を主目的とする定義、実データ、分析実行物 | 各文書は担当する安定情報の正本になり得る。正本の指定は文書管理ルールに従う | 目的、利用者、既存文書との境界、更新責任を Issue で定義し、適切な分類が必要になった時点で追加する |
| [`decisions/`](../../decisions/README.md) | 複数成果物へ継続的に影響する設計・運用判断の記録 | 一時的な検討メモ、作業状況、個別 PR だけに関する理由、一般説明文書 | 整備後の Decision Record が当該判断の正本となる。整備前は関連 Issue に判断を残す | 案内 README は実装済み。後続 Issue でテンプレート、採番、状態管理を決めてから個別記録を追加する |
| [`definitions/`](../../definitions/README.md) | 指標、用語、データモデル、算定式など、再利用する定義 | プロジェクト方針、実データ、分析結果、Notebook | 合意済み定義の正本を置く。概要文書は定義を複製せず参照する | 案内 README は実装済み。対象、形式、検証方法、所有者、更新契機が決まった定義から追加する |
| [`data/`](../../data/README.md) | 再現可能な分析に必要で、Repository での保持が承認された小規模データ、サンプル、スキーマ、取得・生成手順 | 機密・個人・資格情報、ライセンス不明データ、大容量データ、無管理の生成物 | 原データの正本とは限らない。外部正本がある場合は由来と取得方法を記録する | 案内 README は実装済み。機密性、ライセンス、容量、保持期間、Git 管理の妥当性を確認してから追加する |
| [`analytics/`](../../analytics/README.md) | 分析クエリ、Notebook、再現可能な分析コード、レビュー対象の分析結果 | 原データ、指標定義の正本、アプリケーション本体、個人用の試行ファイル | 入力と定義を参照し、分析方法・結果の正本になり得る。指標定義は複製しない | 案内 README は実装済み。目的、入力、出力、実行環境、再現手順、保守責任が決まった分析単位から追加する |
| `.github/` | GitHub 上の Issue・PR・自動化を Repository として管理する設定 | プロジェクト本文、指標定義、データ、GitHub Project の変動状態 | GitHub 機能の構成ファイル。プロジェクト情報の正本を重複保持しない | 別 Lv2「Issue・PR の管理方式を整備する」で運用方式を決定後、必要な設定だけを追加する |

`docs/` 内の番号付き分類は表示順を安易に固定するためには増やしません。既存の `00_project/` はプロジェクト横断文書の領域として維持し、新しい分類は複数の文書を継続的にまとめる必要が生じた場合に限ります。`definitions/`、`data/`、`analytics/` のサブディレクトリも、実際の成果物から共通の分類軸を確認してから設けます。

## 4. 配置判断

新しい成果物は次の順序で配置を判断します。

1. 既存の正本へ追記すべき情報ではないかを確認する。
2. 人が読む説明は `docs/`、永続的な判断は `decisions/`、再利用する定義は `definitions/`、管理可能な入力データは `data/`、分析の実行物・結果は `analytics/` とする。
3. 複数の性質を持つ場合は主な責務を一つ選び、他領域には複製せず相対リンクで参照する。
4. GitHub の運用設定だけは `.github/` とし、成果物本文を置かない。
5. いずれにも当てはまらない場合、新しいトップレベル領域を直ちに作らず Issue で責務境界を決める。

サンプルやテンプレートは、それを利用する領域に置き、ファイル名または本文で用途を明示します。Draft はファイル名やディレクトリ名ではなく、本文の文書版・位置付け・状態で示します。実データは `data/` という名前だけを根拠に格納せず、表の追加条件をすべて満たす必要があります。

## 5. 命名ルール

- ディレクトリ名と通常のファイル名は、原則として意味の分かる英小文字の `kebab-case` とします。
- 各領域の案内文書には、慣例に従い `README.md` を使用します。
- 拡張子は内容と利用ツールに合わせ、Markdown 文書には `.md` を使用します。
- 日付、版番号、`draft`、`final` を、履歴管理だけを目的としてファイル名へ埋め込みません。履歴は Git、状態と版は本文で管理します。
- 略語や連番は、既存の共通語または別途合意した方式がある場合だけ使用します。Decision Record の採番方式は後続 Issue で定めます。
- 同じ意味の単数・複数形や表記揺れを混在させず、既存のトップレベル名と用語を優先します。

## 6. 新設・変更・廃止のルール

### 6.1 ファイル・ディレクトリの新設

Issue で目的、利用者、配置対象、既存の正本との境界、更新責任、追加条件を確認します。ディレクトリは実体を置く時点で案内用 `README.md` とともに作り、将来利用だけを理由とする空構成は作りません。トップレベルの新設は、既存領域では責務が衝突し、複数成果物を継続管理する必要がある場合に限ります。

### 6.2 移動・改名

責務の変化、分類の誤り、命名規則への不一致が利用上の問題になった場合に検討します。見た目の統一だけを理由に既存成果物を移動しません。実施前に `rg` などで Repository 内の参照を確認し、同じ PR で相対リンクと案内を更新します。Git 履歴の追跡可能性と外部からのリンク切れもレビュー対象にします。

### 6.3 廃止・削除

正本としての役割が終了し、必要な情報の移管先または不要である理由が合意された場合だけ実施します。参照元、後継、データ保持義務、再現性への影響を確認し、必要なら本文で廃止状態と後継を案内してから削除します。空になったディレクトリは、近い将来に確定した成果物を置く予定がなければ残しません。

## 7. リンクと正本の扱い

- Repository 内の既存成果物は相対リンク、GitHub Issue・Pull Request・Project など外部対象は完全な URL を使用します。
- 未作成の成果物は存在するようにリンクせず、「後続 Issue で作成予定」のように文章で示します。
- 案内文書や分析成果物では正本を複製せず、必要最小限の要約から正本を参照します。
- リンク、正本、更新責任、同期方法の詳細は `document-governance.md` に従い、本文書では物理配置に必要な規則だけを扱います。

## 8. 実装境界と現在の状態

| 実装単位 | 実施する内容 | 実施しない内容 |
| --- | --- | --- |
| Lv3-1（完了） | 本文書 Draft v0.1 の作成、構成・配置・命名・変更基準の確定 | 他ファイルの変更、各トップレベルディレクトリの物理作成 |
| Lv3-2（完了） | `docs/README.md` と `decisions/README.md` の作成、`decisions/` の物理作成 | Decision Record の詳細様式や個別記録を、合意なく先行作成すること |
| Lv3-3（完了） | `definitions/README.md`、`data/README.md`、`analytics/README.md` と各領域の物理作成 | 実際の指標、実データ、分析ロジック、不要なサブディレクトリの先行作成 |
| 本 Issue（統合、Lv3） | Repository README、文書管理ルール、構成ガイド、各案内 README の参照導線と実装状態を統合 | 未作成成果物へのリンク、本文書と同じ配置ルールの重複管理 |
| 別 Lv2 | `.github/` 配下の Issue・PR テンプレート、workflow などの設計と実装 | プロジェクト成果物の配置変更 |

Lv3-1〜Lv3-3 の初期構成は実装済みです。個別成果物の要件によって本文書の前提を変える必要が生じた場合は、独自判断で構成を増やさず変更 Issue と Pull Request で本文書を更新します。

## 9. 構成変更時の確認事項

- [ ] 成果物の主な責務と配置先が一意に説明できる
- [ ] 既存の正本を重複させていない
- [ ] 未作成成果物を存在するようにリンクしていない
- [ ] 空ファイル・空ディレクトリを将来用途だけで追加していない
- [ ] 命名ルールと既存用語に整合している
- [ ] 移動・改名・削除時に参照元と履歴への影響を確認した
- [ ] データ追加時に機密性、ライセンス、容量、保持条件を確認した
- [ ] `document-governance.md` の正本・参照・更新ルールに整合している
- [ ] Markdown 表示、相対リンク、末尾改行を確認した
- [ ] `git diff --check` を実行した
