# データ活用スケーリング計画 Issue・Pull Request 管理ルール

> **文書版:** Draft v0.3
>
> **位置付け:** 本文書は、GitHub Issue と Pull Request を用いた開発単位、親子関係、ライフサイクル、完了・引継ぎ、および関連付けを定める正本です。情報種別ごとの正本と参照方向は [`document-governance.md`](document-governance.md)、物理配置は [`repository-structure.md`](repository-structure.md) に従います。

## 1. 目的と適用範囲

本文書は、Phase、主要成果物、開発単位、変更差分、完了判断、および親子 Issue 間の引継ぎを一貫して管理するための共通ルールです。本 Repository の GitHub Issue、Pull Request、Project View、成果物、および実装済みの Issue・Pull Request テンプレートに適用します。

Issue は計画と完了判断、Pull Request は差分とレビュー、Project View は現在状態、成果物はマージ後に有効な内容をそれぞれ管理します。Pull Request の `main` へのマージだけでは Issue を完了とせず、更新と親 Issue への引継ぎを終えてからクローズします。

本文書はラベル、Project カスタムフィールド、Automation、Rulesets、Branch Protection、CODEOWNERS、GitHub Actions の具体的な設定を定めません。それらが必要になった場合は、本文書の責務を変更せず、別の Issue で設計・実装します。

## 2. 用語

| 用語 | 定義 |
| --- | --- |
| 正本（Source of Truth） | ある情報を正式に更新・参照する一意の場所 |
| 親 Issue | 複数の成果または作業単位を束ね、統合的なゴールと完了条件を管理する上位 Issue |
| 子 Issue | 親 Issue のゴールを構成し、自身の対象範囲と完了条件を持つ下位 Issue |
| 開発 Issue | 実際の成果物変更を計画し、Pull Request と対応付ける Lv3 パターン1または Lv4 Issue |
| 単純アップデート | Pull Request マージ後、開発 Issue 自身の本文を実装結果に合わせて更新する処理 |
| 引継ぎアップデート | 子 Issue の成果、判断、残課題、後続開始条件を親 Issue の本文へ統合し、子側にも引継ぎ結果を記録する処理 |
| completed | ゴールと完了条件を満たし、必要な引継ぎも完了した Issue のクローズ理由 |
| not planned | 重複、方針変更、対象外化などにより、ゴールを達成せず終了する Issue のクローズ理由 |

## 3. 媒体ごとの責務と参照方向

| 媒体 | 正本とする情報 | 管理しない情報 | 主な参照先 |
| --- | --- | --- | --- |
| Issue | 目的、対象範囲、非対象、完了条件、依存関係、重要な判断、進捗、残アクティビティ、引継ぎ | 成果物本文、コード差分、詳細なレビュー履歴 | 親子 Issue、成果物、Pull Request |
| Pull Request | 変更差分、変更理由、関連 Issue、確認結果、レビュー、マージ判断 | 長期運用ルール、マージ後の成果物本文、親 Issue の統合進捗 | 開発 Issue、変更対象の成果物 |
| Project View | 現在の重点、状態、横断的な進捗 | 詳細な目的、完了条件、判断履歴 | 対応する Issue |
| 成果物 | `main` で有効な仕様、文書、コード、定義 | 作業中の進捗、レビュー会話 | 関連する安定情報の正本 |
| テンプレート | 起票・作成時の入力補助、記載漏れ防止 | 共通ルールそのもの、個別 Issue の最新状態 | 本文書 |

参照方向は原則として **Project View → Issue、Issue → 成果物と Pull Request、Pull Request → Issue と変更対象、テンプレート → 本文書** とします。実装済みの [Lv1〜Lv4 Issue テンプレート](../../.github/ISSUE_TEMPLATE/) と [Pull Request テンプレート](../../.github/pull_request_template.md) は、この参照方向に従う入力補助です。Issue や Pull Request に成果物本文または本文書のルールを複製せず、必要最小限の要約と参照先を記載します。

## 4. Issue 階層と作成条件

| レベル | 責務 | 作成条件 | 親子関係と完了判断 |
| --- | --- | --- | --- |
| Lv1 | Phase と、その統合的な成功状態を管理する | 独立した Phase の目的、対象範囲、主要成果物、終了条件を管理するとき | 最上位。必要な Lv2 の成果を統合し、Phase の完了条件で判定する |
| Lv2 | Phase を構成する主要成果物または機能モジュールを管理する | 複数の標準開発単位を束ねて主要成果物の完成を判定するとき | Lv1 の子、Lv3 の親。子の完了だけでなく統合状態を確認する |
| Lv3 | 設計・実装・レビューが可能な標準開発単位を管理する | 明確なゴールと完了条件を持つ成果を実装するとき | Lv2 の子。パターン1またはパターン2を選択する |
| Lv4 | 独立して着手、レビュー、完了判定できる個別タスクを管理する | Lv3 を複数 PR、並行作業、または独立した完了判定へ分ける必要があるときだけ | パターン2の Lv3 の子。原則として 1 PR で完了する |

上位 Issue は子 Issue の一覧だけでなく、統合後のゴール、依存関係、残アクティビティを管理します。子 Issue を作成するときは、親を明示し、親側の Issue ツリーまたは残アクティビティにも登録します。階層は作業量や見た目ではなく、責務と完了判定の境界で選択します。

### 4.1 Phase の Just-in-Time 起票

#### 原則と媒体の責務

将来 Phase の詳細な Lv1 Issue は、着手判断に必要な情報がそろう前に一括作成せず、次に着手する Phase を判断するときに Just-in-Time で作成します。先行 Phase の完了だけを理由に次 Phase を自動起票しません。準備作業を Issue として管理する必要がある場合も、その具体的な実行単位に限って起票し、未評価の Phase 全体を確定した計画として扱いません。

各媒体は次の責務を持ちます。

| 媒体 | 責務 | 管理しない情報 |
| --- | --- | --- |
| [ロードマップ](roadmap.md) | 将来 Phase を含む方向、目的、価値、成果ゲート、順序、主要な依存関係、引継ぎ、および現時点の確度 | 個別作業の現在状態、担当、詳細な実行計画 |
| Milestone | 着手対象となった Phase の Issue 群を成果ゲート単位で束ねる期間横断の目印 | Phase の詳細仕様、個別 Issue の完了判断 |
| GitHub Issue | 現在または直近に実行する Phase・成果物・作業の目的、対象範囲、実行計画、現在状態、完了判断 | 未評価の将来 Phase の詳細計画、成果物本文 |

ロードマップを Phase 間計画の正本とし、Milestone や Issue に同じ説明を複製しません。Lv1 Issue 同士は親子関係にせず、ロードマップに記載した前後関係、開始条件、依存関係、および引継ぎで接続します。

#### Lv1 Issue の起票トリガー

次 Phase の Lv1 Issue は、次の項目をすべて確認し、現在または直近に実行する具体的な単位として管理できる場合に作成します。項目を満たさない場合は起票を延期し、不足情報または再評価条件を現在の Issue の残アクティビティとして管理します。

- 直前 Phase の成果、判断、学び、未解決事項、および引継ぎを確認できる
- ロードマップ上の次 Phase の目的、期待する価値、成果ゲート、順序が最新状況でも妥当である
- 他の候補と比較した優先度、および利用可能な人員・情報・環境を踏まえた実行可能性を説明できる
- 開始条件を満たす見込みと、主要な依存関係、制約、後続への引継ぎを説明できる
- Lv1 の対象範囲と完了条件を定め、Issue として追跡可能な Lv2 以下の具体的な実行単位へ分解できる

この確認は、起票を承認する特定の役職や定例会議を要求しません。起票判断を行う担当者は、確認結果と未確定事項を作成する Lv1 Issue に記録します。

#### 起票時の確認項目

Lv1 Issue の作成時は、既存テンプレートの項目を用いて少なくとも次を確認します。詳細は最新の事実に基づいて記載し、ロードマップの説明は必要最小限の要約と相対リンクで参照します。

- Phase 名称、目的、期待する価値、およびロードマップ上の位置付け
- 開始条件、完了条件、対象範囲、非対象
- 先行 Phase の成果と学び、主要な依存関係、制約、次 Phase への引継ぎ
- ロードマップの目的、順序、成果ゲート、依存関係を変更する必要の有無
- 対応する Milestone、親子・関連 Issue、正本となる文書と成果物
- 現時点では確定できない事項、その確認方法、および判断時期

着手判断に不要な日程、工数、担当、予算、KPI 算定式、データソース、画面、技術方式は、根拠がそろう前に先行確定しません。実行に必要となった時点で、適切な Lv2 以下の Issue または成果物において決定します。

#### 起票前後と Phase 完了時の更新責務

1. 起票判断でロードマップ上の目的、順序、成果ゲート、依存関係、引継ぎ、または確度の変更が必要と判明した場合、Lv1 Issue の起票前または同じ変更単位でロードマップを更新します。変更不要の場合は、確認した旨を Lv1 Issue に記録します。
2. 起票時に対象 Phase の Milestone と既存の関連 Issue を確認し、必要な関連付けを行います。Milestone の具体的な作成・変更は既存運用に従い、本ルールでは新しい承認者や定例作業を設けません。
3. Lv1 Issue 作成後、Repository README、ロードマップ、GitHub Project README などに現在 Phase への参照導線を設ける必要がある場合は、別の開発 Issue で正本と入口の責務を保って更新します。起票だけを理由に、同じ説明を複数媒体へ複製しません。
4. Phase 完了時は、完了した Lv1 Issue の単純アップデートと必要な引継ぎを行ったうえで、次 Phase の起票トリガーを最新の成果、環境、価値仮説、優先度に基づいて再評価します。条件を満たさない場合やロードマップを見直す場合は、次 Phase を自動起票しません。

## 5. Lv3 パターンと Issue 分割

### 5.1 パターン1：1つの開発 Issue と Pull Request で完了

Lv3 は原則としてパターン1を選択します。成果が一体として設計・レビューでき、1つの Pull Request で安全に変更でき、独立した子タスクの完了判定を必要としない場合、Lv4 を作成しません。Lv3 自身を開発 Issue とし、実装、レビュー、単純アップデート、親 Lv2 への引継ぎまで管理します。

### 5.2 パターン2：複数の Lv4 を統合

次のいずれかが必要な場合はパターン2を選択し、Lv3 を統合管理の親 Issue、Lv4 を開発 Issue とします。

- 成果を安全にレビューできる複数の Pull Request へ分ける必要がある
- 担当、着手条件、依存関係が異なる作業を並行または順次管理する必要がある
- 各作業に独立したゴール、対象範囲、完了条件がある
- 共有箇所への変更順序や、複数成果の統合確認を明示的に管理する必要がある

パターン2の Lv3 には、Lv4 の一覧、依存関係、想定マージ順序、共有ホットスポット、統合確認、残アクティビティを記載します。すべての Lv4 が閉じても、Lv3 の統合条件と親への引継ぎが未完了なら Lv3 は閉じません。

### 5.3 分割しない条件

次の事情だけを理由に Lv4 へ分割しません。

- 文書の章、チェック項目、コミット、変更ファイルが複数ある
- 作業手順をチェックリストへ細分化できる
- Issue 本文が長い、または実装に一定の時間を要する
- 分割すると同一成果物や共通定義が一時的に不整合になる
- 各部分を単独では利用・レビュー・完了判定できない

途中でパターン変更が必要になった場合は、変更理由、分割対象、依存関係、完了条件を Lv3 に先に記録してから Lv4 を作成します。

## 6. Issue ライフサイクル

### 6.1 起票と着手

1. Issue のレベルと親 Issue を決め、目的、ゴール、対象範囲、非対象、完了条件、依存関係を記載します。
2. Lv3 ではパターン1・2を選択します。子 Issue がある場合、親子双方から関係を確認できるようにします。
3. 既存の正本、関連 Issue・Pull Request、共有ホットスポット、未確定事項を確認します。
4. 着手可能条件を満たしたら Project View の状態を更新し、開発ブランチを作成します。

起票時点で実施しない内容は非対象として明示します。対象範囲または完了条件を変更する場合は、変更理由と親・子・後続作業への影響を Issue の本文へ反映してから作業を続けます。

### 6.2 開発から `main` マージまで

1. 開発 Issue の範囲だけを変更し、必要に応じて Draft Pull Request を作成します。
2. Pull Request を Issue へ関連付け、差分、確認結果、残作業を更新します。
3. Ready for review の条件を満たしてレビューを依頼し、指摘と修正結果を Pull Request に残します。
4. マージ前最終確認後、承認された差分を `main` へマージします。

マージは成果物反映の完了であり、Issue ライフサイクルの完了ではありません。自動クローズされた場合も、後述の更新と引継ぎを実施し、必要なら再オープンして正しい状態へ戻します。

### 6.3 単純アップデート

マージ後、開発 Issue 自身を次のとおり更新します。

- 実装した内容と対象 Pull Request を実装履歴へ反映する
- 残アクティビティから完了した項目を除き、未完了項目を最新化する
- 完了条件を実際の確認結果に基づいて更新する
- 確定した設計・運用判断、確認結果、非対象、未確定事項を本文の該当箇所へ反映する
- 後続作業の開始条件と Repository 外の手動作業を明示する

コメントの追記だけで本文の古い状態を残しません。成果物本文や Pull Request のレビュー履歴は複製せず、参照先と完了判断に必要な要約だけを記載します。

### 6.4 引継ぎアップデート

単純アップデート後、親子双方を更新します。

**親 Issue で行う処理:**

- 子 Issue の成果、対象 Pull Request、確定した重要判断を実装履歴へ統合する
- 完了した活動を残アクティビティから移し、次の活動と開始条件を更新する
- 子の未確定事項、リスク、依存関係を、親で管理すべきものだけ引き継ぐ
- 親のゴール、完了条件、統合状態への影響を更新する

**子 Issue で行う処理:**

- 引継ぎ先の親 Issue と、親へ反映した内容を記録する
- 自身の残アクティビティが空であることを確認する
- ゴール、完了条件、Repository 外の必要作業がすべて完了したことを確認する

引継ぎはコメントだけで済ませず、親子それぞれの本文を最新状態にします。親がない Lv1 では、関連する Project View と上位計画への必要な反映を完了条件として扱います。

### 6.5 クローズ

単純アップデートと引継ぎアップデートを終え、ゴールと完了条件を満たした Issue は `completed` でクローズします。未達のまま終了する場合は `not planned` とし、重複先、方針変更、対象外化などの理由と、残る影響の引継ぎ先を本文へ記載します。

`open` は計画中、実施中、レビュー中、マージ後作業中、またはブロック中を含みます。`closed` は作業中ステータスの代用にせず、`completed` または `not planned` の理由を明確にします。再開が必要な場合は再オープンし、理由、残アクティビティ、親 Issue への影響を更新します。

## 7. Pull Request ライフサイクル

### 7.1 Draft

作業途中の差分を共有し、設計、依存関係、統合リスクを早期確認したい場合は Draft で作成します。Draft でも関連 Issue、目的、対象範囲、主な変更、確認方法、未完了事項を記載します。レビュー可能でない差分を承認依頼しません。

### 7.2 Ready for review

次を満たした時点で Ready for review にします。

- 関連 Issue の対象範囲を実装し、意図した差分だけが含まれている
- 必要なテストまたは文書変更の代替確認を実施し、結果を記載している
- 未完了事項、既知の制約、手動作業、非対象が明確である
- セルフレビューで命名、リンク、正本、既存ルールとの整合を確認している

### 7.3 レビューと修正

レビュアーは、Issue のゴールと完了条件への適合、差分の妥当性、正本の重複、テスト結果、後方互換性、非対象への混入を確認します。作成者は指摘ごとに修正または対応しない理由を示し、変更で確認結果が無効になった場合は再確認します。重要な設計判断は Pull Request の会話だけに残さず、Issue または該当する成果物へ反映します。

### 7.4 マージ前最終確認

作成者とマージ判断者は、次を確認します。

- 必要な承認があり、未解決のレビュー指摘がない
- ブランチがマージ可能で、最新差分に対する確認結果が有効である
- Pull Request のタイトルと本文が最終差分を表し、関連 Issue が正しい
- マージ後の単純アップデート、引継ぎ、手動同期の担当と順序が明確である
- 自動クローズが意図せず発生しない

### 7.5 マージ後作業

`main` へのマージ後は、成果物の反映を確認し、必要な Repository 外の同期または Project View 更新を実施します。その後、Issue の単純アップデート、親への引継ぎ、子 Issue のクローズをこの順序で行います。マージ済み Pull Request に長期的な最新状態を追記し続けず、Issue と成果物の正本を更新します。

Pull Request をクローズしてマージしない場合は、理由、代替 Pull Request、Issue の残アクティビティへの影響を記載します。

## 8. 命名と関連付け

### 8.1 Issue

Issue タイトルは、必要なプロジェクト名・レベル・短い種別を先頭に置き、達成する内容を日本語の動詞で具体的に表します。

```text
[Data Value Scaling][Lv3][Process] Issue・PR管理ルールを定義する
```

種別は固定ラベル体系とはせず、`Process`、`Docs`、`Data`、`Analytics` など責務を識別できる短い英語を使用します。同じ親配下では表記をそろえます。

### 8.2 ブランチ

ブランチ名は次の形式を基本とし、英小文字の `kebab-case` で Issue 番号と目的を識別できるようにします。

```text
<prefix>/issue-<number>-<short-purpose>
```

`<prefix>` は担当者または利用環境で定められた識別子を使用します。1ブランチへ無関係な Issue の変更を混在させず、パターン2では Lv4 ごとにブランチを分けます。

### 8.3 Pull Request

Pull Request タイトルは変更後の成果が分かる簡潔な動詞表現とし、Issue タイトルを機械的に複製する必要はありません。本文には原則として次を記載します。

```text
Related Issue: #<number>
```

`Related Issue` は関連付けであり、自動クローズを発生させません。単純アップデートと親への引継ぎより先に Issue が閉じることを避けるため、`Closes`、`Fixes`、`Resolves` などの自動クローズキーワードは原則使用しません。

例外は、親への引継ぎも Repository 外作業もなく、マージ時点で Issue の本文、ゴール、完了条件、Project View がすべて最終状態となることをマージ前に確認できる場合です。例外を使用する場合は、Pull Request に理由と確認結果を明記します。階層を持つ開発 Issue では、原則どおり手動クローズします。

## 9. 状態管理

| 対象 | 状態 | 判断基準 |
| --- | --- | --- |
| Issue | open | 未着手、進行中、レビュー中、ブロック中、またはマージ後の更新・引継ぎが残っている |
| Issue | closed / completed | ゴール、完了条件、単純アップデート、必要な親への引継ぎがすべて完了した |
| Issue | closed / not planned | ゴール未達で終了し、理由と影響の引継ぎ先を記録した |
| Pull Request | Draft | 差分または確認が未完了で、正式レビューを依頼していない |
| Pull Request | Open / Ready for review | レビュー条件を満たし、承認・マージ判断を待っている |
| Pull Request | Merged | 承認された差分が `main` へ反映された。Issue の完了を自動的には意味しない |
| Pull Request | Closed | マージせず終了し、理由と代替・残作業を記録した |

Project View はこれらの正本を置き換えず、現在状態を表示します。状態変更時に View の更新が必要な運用であれば更新し、Repository 外で未実施の更新は Issue の残アクティビティへ記録します。

テンプレートは本文書の共通ルールを再定義しません。ラベル、Automation、Project フィールド、Rulesets、CODEOWNERS、GitHub Actions などは未実装であり、必要な場合は後続 Issue で対象範囲と運用方式を定めます。

## 11. 運用チェックリスト

### 11.1 Issue 起票・分割

- [ ] レベル、親 Issue、ゴール、完了条件を一意に説明できる
- [ ] Lv3 のパターン選択と、Lv4 を作成する・しない理由が明確である
- [ ] 対象範囲、非対象、依存関係、共有ホットスポットを確認した
- [ ] 親子双方から関係と残アクティビティを確認できる

### 11.2 Pull Request

- [ ] `Related Issue: #<number>` で開発 Issue を関連付けた
- [ ] 差分、変更理由、確認結果、非対象、マージ後作業を記載した
- [ ] Ready for review とマージ前最終確認の条件を満たした
- [ ] 自動クローズキーワードを原則使用していない。例外時は理由を記載した

### 11.3 マージ後・クローズ

- [ ] 開発 Issue を単純アップデートした
- [ ] 親子双方で引継ぎアップデートを完了した
- [ ] Project View と Repository 外の必要作業を確認した
- [ ] 残アクティビティが空で、ゴールと完了条件を満たした
- [ ] `completed` または `not planned` の適切な理由でクローズした

文書のみの変更では CI や E2E の代わりに、`git diff --check`、相対リンク先の存在、Markdown の見出し・表・箇条書き・コードブロック、末尾改行、および既存の文書管理ルール・Repository 構成ガイドとの整合を確認し、理由と結果を Pull Request に記録します。
