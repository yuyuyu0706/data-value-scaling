# データ活用スケーリング計画 全体ロードマップ

> **文書版:** Draft v0.1
>
> **位置付け:** 本文書は、Phase 0〜6の実行順序、成果物、開始・完了条件、依存関係および引継ぎを管理する正本候補である。日程表ではなく、成果と判断ゲートに基づいて次のPhaseへ進むための計画として扱う。

## 1. 目的

本ロードマップは、データ資本から事業価値への変換効率を捉え、小規模なユースケースを継続利用・拡大・横展開・共通化へ育てるために、Phase 0〜6で何を明らかにし、何を成果として次へ引き継ぐかを示す。

日付、工数、担当者を先に固定するのではなく、各Phaseの目的、解決する問い、主要成果物、開始条件、完了条件、依存関係および引継ぎを共通形式で定義する。これにより、前Phaseの学びを反映しながら、後続のLv1 Issueを同じ骨格で具体化できるようにする。

## 2. 位置付けと責務分割

| 媒体 | 責務 |
| --- | --- |
| 本ロードマップ | Phase間の実行順序、成果ゲート、依存関係、引継ぎの正本候補 |
| Repository README | プロジェクトとPhase概要を把握し、各正本へ移動するための入口 |
| プロジェクト憲章 | 背景、目的、主要概念、基本原則、対象範囲、成功状態の長期的・安定的な判断基準 |
| 各Lv1 Issue | ロードマップの該当Phaseを具体化した実行計画、アクティビティ、現在状態、完了判断 |

ロードマップは変動する進捗一覧や詳細な算定式を重複して保持しない。現在状態はGitHub Project Viewと各Issue、指標の算定式・データ要件は後続の設計文書で管理する。

## 3. 対象者と読み方

### 3.1 対象者

- 事業責任者・意思決定者：各Phaseが提供する判断材料と、資源配分へ統合するまでの道筋を確認する。
- ユースケースのオーナー・利用部門：価値仮説、成果、定着、学習がどのモデルで扱われるかを確認する。
- データ・分析・AI・プラットフォーム担当者：共通定義と各モデルの責務、再利用可能な成果の引継ぎを確認する。
- ガバナンス・セキュリティ・財務等の支援者：価値、コスト、リスク、データ資本を段階的に扱う境界を確認する。
- プロジェクトの設計・運営担当者：PhaseのLv1 Issueを起票し、開始・完了判断やロードマップ更新を行う。

### 3.2 読み方

1. 「Phase一覧」で全体の基本順序と確度を把握する。
2. 着手候補のPhaseについて、開始条件を満たす根拠と依存関係を確認する。
3. 実行中は主要成果物ではなく完了条件を判断ゲートとして用い、成果が利用可能な状態かを確認する。
4. 完了時は次Phaseへの引継ぎをLv1 Issueへ具体化する。
5. 後続Phaseで新たな事実を得た場合は、先行成果や共通定義への還流要否を確認する。

「現時点の確度」は、方向性の成熟度を次の語彙で示す。これはIssueの進捗状態ではない。

| 確度 | 意味 |
| --- | --- |
| 確定 | 既存の合意・成果に基づき、現時点で実行の基準として利用できる |
| 計画 | 目的と成果ゲートは計画として利用できるが、前Phaseの学びによる具体化が必要 |
| 仮説 | 方向性を示す仮説であり、先行Phaseの結果を基に妥当性の確認が必要 |

### Phase 2：データ価値キャッシュフローMVPを構築する

#### 目的

データ資本と資源の投入から、ユースケースを通じて事業価値が実現し、学習や再利用可能な資産が還流するまでの流れを、最小限のモデルで捉える。

#### 解決する問い

- 何をいつ投入し、どの価値仮説からどの成果がいつ実現したか。
- 価値実現までの時間、停滞、遅延および還流をどのように捉えるか。
- 次の投資・改善判断に必要な最小限の流れを、取得可能な情報で説明できるか。

#### 主要成果物

- データ価値キャッシュフローMVPの概念モデル。
- 代表ユースケースに対する投入、価値仮説、実現価値、時間、学習・資産還流の試行結果。
- 利用する意思決定、前提、データ取得上の制約、改善候補の記録。

#### 開始条件

- Phase 1の共通定義と判断単位が利用できる。
- MVPで検証する代表ユースケースと、利用する意思決定が選定されている。

#### 完了条件

- 代表ユースケースについて投入から価値実現・還流までの流れを一貫して記述できる。
- 流れの可視化が、継続、改善または追加検証の具体的な判断材料になることを確認している。
- 測定不能・不確実な項目を推測で埋めず、制約と次の検証方法を記録している。
- Phase 1の共通定義および後続モデルへ反映すべき学びが整理されている。

#### 依存関係

- Phase 1の共通定義に依存する。
- Phase 3〜5へ価値実現の流れと検証結果を提供し、それらの学びによる見直しを受ける。

#### 次Phaseへの引継ぎ

- 実現価値、時間、投入、学習・還流に関するMVPと検証結果。
- 価値実現スコアカードで併せて評価する価値創出、スケール、ポートフォリオ、基盤効率の観点。
- 共通定義へ還流する変更候補と、未解決の測定制約。

#### 現時点の確度

**仮説。** モデルの責務とMVPの方向性を示している。項目、表現、データソース、算定方法はPhase 1の結果とPhase 2の検証で定める。

### Phase 3：価値実現スコアカードを構築する

#### 目的

#### 解決する問い

- ユースケースの成果と現在地を、どの観点の組合せで過不足なく説明できるか。
- 先行する変化、最終成果、定着、コスト、リスクおよび学習をどう区別するか。
- 観点の違うユースケースを、単純な総合点に依存せずどう比較し判断するか。

#### 主要成果物

- 価値実現スコアカードの観点と評価構造。
- 代表ユースケースへの適用結果と、継続・改善・拡大等の判断例。
- 評価の根拠、証拠の確度、比較上の制約、更新候補の記録。

#### 開始条件

- Phase 1の共通定義、判断単位および共通項目が利用できる。
- Phase 2で確認した価値実現の流れ、または同等の検証可能な記録を参照できる。

#### 完了条件

- 代表ユースケースの価値創出とスケールの状態を複数観点で説明できる。
- 各観点が利用する意思決定と結び付き、評価根拠と不確実性を追跡できる。
- スコアが規模・利用量の増加や単一の総合点を目的化していない。
- Phase 1・2および後続モデルへ反映すべき学びが整理されている。

#### 依存関係

- Phase 1の共通定義を必須とし、Phase 2の価値実現の流れを基本的な入力とする。
- Phase 4・5のコスト・データ資本の観点を取り込み、必要に応じて評価構造を見直す。

#### 次Phaseへの引継ぎ

- 価値実現の評価観点、根拠、確度および代表ユースケースの評価結果。
- データ活用損益計算書で価値とコストの関係を検証するための成果・投入観点。

#### 現時点の確度

**仮説。** 複数観点で判断を支援する責務は明確である。評価項目、尺度、重み付けの要否は先行Phaseの事実を基に検証する。

### Phase 4：データ活用損益計算書を構築する

#### 目的

- 財務価値と非財務価値、不確実な価値をどのように区別して判断に用いるか。
- 継続、改善、拡大、保留、終了の判断に必要な収益性・効率性の情報は何か。

#### 主要成果物

- データ活用損益計算書の管理上の構造と項目関係。
- 代表ユースケースまたはポートフォリオへの適用結果と判断例。
- 価値・コストの範囲、期間、配賦、不確実性および会計制度との境界の記録。

#### 開始条件

- Phase 1の共通定義が利用できる。
- Phase 2・3から、価値実現、投入、成果、評価根拠に関する検証結果を参照できる。

#### 完了条件

- 代表対象について、実現価値と創出・維持コストの関係を一貫した範囲で説明できる。
- 財務・非財務価値と不確実性を区別し、意思決定に用いた根拠を追跡できる。
- 正式な財務諸表、会計上の利益または制度上の投資審査を表すものではないことが明確である。
- Phase 1〜3およびPhase 5へ反映すべき学びが整理されている。

#### 依存関係

- Phase 1の共通定義を必須とし、Phase 2・3の価値実現と評価結果を基本的な入力とする。

#### 次Phaseへの引継ぎ

#### 現時点の確度

### Phase 6：データ活用スケーリング計画へ統合する

#### 目的

#### 解決する問い

- 各モデルの結果を、重複や矛盾なくどの判断プロセスで組み合わせるか。
- 個別ユースケースとポートフォリオ全体の優先順位・相互依存をどう調整するか。
- 判断、行動、結果、学習をどのように記録し、次の資源配分と価値検証へ還流するか。

#### 主要成果物

- 共通定義、データ価値キャッシュフロー、価値実現スコアカード、データ活用損益計算書、データ活用バランスシートの統合構造。
- 継続・改善・拡大・横展開・共通化・保留・終了と資源配分の判断フロー。
- 代表ユースケースおよびポートフォリオでの統合検証結果、運用上の役割・更新契機・改善候補。

#### 開始条件

- Phase 1の共通定義を利用できる。
- Phase 2〜5の各モデルが代表対象で検証され、統合に必要な成果、制約、未確定事項が引き継がれている。
- モデル間の重大な用語・判断単位の不整合が解消されているか、統合時の扱いが合意されている。

#### 完了条件

- 代表ユースケースとポートフォリオについて、各モデルの根拠から次の行動と資源配分を一貫して説明できる。
- 判断が事業価値を起点とし、規模だけを目的化せず、コスト、リスク、成熟度、相互依存および再利用を考慮している。
- 判断結果と学習がデータ資本および各モデルへ還流し、次回の評価・資源配分を改善できる。
- 統合運用の役割、更新契機、制約、未確定事項および次の改善サイクルが記録されている。

#### 依存関係

- Phase 1〜5の成果と横断的な整合確認に依存する。
- 統合検証で得た学びはPhase 1の共通定義とPhase 2〜5の各モデルへ還流する。

#### 次Phaseへの引継ぎ

- Phase 6の後に新たな番号のPhaseを先行設定しない。
- 統合した計画、判断記録、学習、未確定事項および改善Backlogを、継続的な運用・見直しサイクルへ引き継ぐ。
- プロジェクト憲章の成功状態に対する到達度と、次に検証すべき価値仮説を引き継ぐ。

#### 現時点の確度

**仮説。** 統合対象と接続する意思決定は明確である。最終成果物の形式、利用画面、運用責任はPhase 2〜5の検証後に具体化する。

## 6. Phase間の依存関係と反復原則

基本順序は次のとおりとする。

```text
Phase 0（管理基盤）
  ↓
Phase 1（共通定義）
  ↓
Phase 2（価値実現の流れ）
  ↓
Phase 3（複数観点の評価）
  ↓
Phase 4（価値とコストの関係）
  ↓
Phase 5（データ資本の蓄積と状態）
  ↓
Phase 6（意思決定・資源配分への統合）
```

この順序は成果の依存を示す基本線であり、完全な一方向工程を意味しない。次の原則で反復する。

- Phase 1の共通定義はPhase 2〜5の共通基盤とするが、各モデルで得た事実に基づき意味・粒度・項目を更新できる。
- Phase 2〜5は先行Phaseの利用可能な成果を入力とする。後続モデルの学びが先行モデルの前提・項目・境界へ影響する場合は、変更理由と影響を記録して見直す。
- 並行着手は、必要な共通定義と入力が利用でき、責任範囲、統合点、変更時の調整方法を各Lv1 Issueで明確にできる場合に限る。単に日程を短縮する目的では行わない。
- 先行Phaseを見直しても、そのPhaseの完了を無条件に取り消さない。変更の大きさ、後続成果への影響、再検証の必要性をIssueで判断する。
- Phase 6は主要モデルが存在するだけでは開始しない。代表対象での検証、モデル間の整合、および制約・未確定事項の引継ぎを開始ゲートとする。

## 7. 更新ルール

### 7.1 更新契機

- 前Phaseの完了判断または次Phaseの開始判断を行うとき。
- 代表ユースケースや主要モデルの検証で、前提と異なる事実または新たな学びを得たとき。
- Phaseの目的、主要成果物、開始・完了条件、依存関係、引継ぎまたは確度が変わるとき。
- プロジェクト憲章の目的・原則・対象範囲、またはRepository READMEのPhase名称との不整合が生じるとき。

### 7.2 更新方法

1. 変更の根拠となる事実、対象Phase、利用者および意思決定への影響をIssueへ記録する。
2. 前後Phase、共通定義、主要モデル、Lv1 Issue、入口文書への影響を確認する。
3. 本文書の正本変更をPull Requestでレビューし、変更理由と確認結果を残す。
4. mainへの反映後、関係するIssueと入口の更新要否を確認する。

日程、工数、担当者、詳細な算定式、データソース、画面・実装方式は、判断に必要となった段階で各Lv1 Issueまたは設計文書へ具体化し、本ロードマップへ重複させない。Phase番号・名称の変更やプロジェクトの目的・対象範囲に影響する変更は、親Issueとプロジェクト憲章への影響を先に確認する。

## 8. 未確定事項・後続判断

- Phase 1〜6のLv1 IssueにおけるLv2構成、日程、担当、優先順位。
- Phase 1の共通項目、代表ユースケース、記録形式および測定可能性の検証方法。
- Phase 2〜5を並行実施できる具体的な条件と、各モデル間の統合契約。
- 各モデルの算定式、目標値、データソース、更新頻度、画面・実装方式。
- Phase 6の最終成果物の形式、利用画面、運用責任および改善サイクル。
- ロードマップの重要変更をDecision Recordとして管理する基準。

これらは推測で確定せず、必要な情報、判断責任および決定の契機が明らかになった段階で、該当PhaseのIssueまたは設計文書に記録する。
